# Design

## Context

动机见 `proposal.md` 的 Why。以下是塑造本方案的现状与约束。

代码现状（均在 `src/pet/`）：

- 绘制契约是"设备像素空间"。`run.ps1` 带 `-Dsun.java2d.uiScale=1`，`SPRITE_SCALE = 2`，
  精灵图按整数倍最近邻放大，所以绘制坐标等于物理像素、像素不发虚。骨架求值必须沿用这个契约。
- 角色由 `BodyRig` 从单张 105×123 精灵图剪出 4 片：躯干、提灯（杖＋手）、左右小腿。
  `erase()` 把杖区与腿区从躯干上挖空，因此关节一旦多转就会露出透明洞——现在靠摆幅小来回避。
- `PetWindow` 每帧合成：整体 `translate` ＋ `rotate(tilt)`，再按腿的髋枢轴、提灯的握点各自旋转贴图。
  没有任何网格或仿射变形，全部是刚体。
- `Pendulum` 已经是带重力回复、外部加速度耦合、阻尼与限位反弹的单摆，目前只挂在提灯上。
- 窗口形状不是每帧剪影：`envelopeShape` 预先覆盖整体倾斜 ±16 度与提灯摆动的极限，
  `applyShape()` 只在状态变化时 `setShape`。窗口尺寸由 `headroom / leftRoom / rightRoom`
  与 `groundX / groundY` 决定。
- 鼠标拖拽现在是"整窗平移"：只记 `pressScreen / pressWindow` 与一个 `dragging` 布尔，
  姿态不变；`bodyAt()` 是一个固定矩形包围盒，不按当前外形判断。
- 纵向位置恒等于 `groundLine - groundY`，拖动结束后角色会自动回到屏幕底部基准线。

素材与工具现状：

- `assets/素材原图/character-reference-2048.png`：2048×2048，**黑底**。
- `tools/prepare-sprite.ps1` 的泛洪判据是"接近白色"（`-BgThreshold 238`），对黑底立绘无效。
- 现有 105×123 精灵图里有 7595 种颜色，说明它是缩小后的插画、不是限色板像素画，
  因此 AI 路线不必凑色板，但边界与高光的还原仍然要验收。

外部环境：

- ComfyUI 0.39.0 便携版在 `E:\AI\ComfyUI_windows_portable`，自带 Python 3.13 与 PyTorch，CUDA 可用；
  `models/` 下目前没有任何生成模型；未安装节点管理器；自带工作流模板 609 个，
  其中包含本地的补洞与图像编辑模板（如 `flux_fill_inpaint_example.json`、
  `image_qwen_image_instantx_inpainting_controlnet.json`、`image_qwen_image_edit_2509.json`、
  `flux_kontext_dev_basic.json`），不装自定义节点即可开工。
- 硬件：RTX 4060 Laptop，8188 MiB 显存；C 盘剩余约 18 GB，因此模型与产出放 D 或 E 盘。

## Goals / Non-Goals

**Goals:**

- 关节可连续弯折的骨架驱动动画，逐帧求值，与显示刷新同步。
- 发丝、袖子、袍摆、提灯用链式阻尼动力学驱动，带惯性滞后并收敛。
- 动作可无缝循环：拎起悬挂、招手、以及既有的踱步等动作。
- 素材产线可重复执行，像素补全只作用于缺失区域。

**Non-Goals:**

- 不做 AI 逐帧视频生成。ComfyUI 在本方案里只产出静态素材，不产出动画。
- 不引入任何 Java 第三方依赖（不引 Spine、libGDX 等），`build.ps1` 继续只用 `javac`。
- 不做 3D、不做 Live2D、不做口型或说话动作、不做坐下动作。
- 不做多显示器适配，也不处理角色素材的版权与仓库推送策略。
- 拆件粒度只按本次动作范围（拎起、招手、既有动作迁移）确定。
  后续若新增说话、坐下一类动作，需要重新评估骨树与拆件粒度。

## Decisions

### 1. 骨骼与蒙皮放在 Java 运行时自己算

自己写一个很小的 2D 骨架求值器：骨树、双骨 IK、按顶点权重做三角网格变形。

- 为什么：项目契约是零第三方依赖，`build.ps1` 只用 `javac`；只有实时求值才能同时满足
  "循环首尾无缝"与"对鼠标即时反应"两个验收点；烘焙序列帧会让素材量与状态组合爆炸。
- 备选：Spine 或 DragonBones 运行时（一个收费、一个已停维护，且破坏零依赖）；
  Blender 绑骨烘焙成序列帧（要新增工具链与一道烘焙工序，还丢掉实时交互）。

### 2. 形变分级：只有四肢关节用蒙皮，发丝/袖/袍摆/提灯用纯链式骨骼

```
   root（站立时锚在脚下；拎起时锚在鼠标抓点）
    +- spine 躯干（1-2 节，可轻微弯）
    |   +- head 头
    |   |   +- hair 发丝链 A-B-C        <- 纯链式，每节一个阻尼单摆
    |   |   +- 角 / 发饰                <- 刚体贴图
    |   +- 远侧臂 upperArm -> forearm -> hand   <- 关节蒙皮
    |   +- 近侧臂 upperArm -> forearm -> hand   <- 关节蒙皮
    |   |        +- 提灯 staff（复用现有 Pendulum，挂点 19,66）
    |   +- 袍摆链 coat L / coat R        <- 纯链式
    +- 近侧腿 thigh -> shin -> foot       <- 关节蒙皮
    +- 远侧腿 thigh_far -> shin_far -> foot_far
```

- 为什么：链式骨骼是实现"关节灵活"最便宜的部分，而这个角色最抢眼的动感恰好全在链上
  （长发、宽袖、长袍飘带、提灯）；真正非蒙皮不可的只有肩、肘、髋、膝四处。
- 备选：全部蒙皮（工作量大、收益低）；全部保持刚体（就是现状，做不到关节灵活）。

### 3. 链式节复用 Pendulum

把 `Pendulum` 的"外部加速度"输入从手部加速度换成父节点末端的加速度，即可串成链。

- 为什么：它已有重力回复、耦合、阻尼与限位反弹，参数少、不会失控，且在生产环境跑过。
- 备选：新写一套弹簧-阻尼链（重复造轮子）；改用 verlet 积分（更简单，但丢掉现有的限位与阻尼语义）。

### 4. rest pose 采用现有立绘的侧身持杖站姿

- 为什么：骨骼可以以任意姿势作为 rest pose；桌宠本身就是站立踱步，侧身持杖合乎角色设定；
  这样省掉姿势迁移模型和随之而来的整图风格一致性问题。
- 备选：先用图像编辑模型把立绘转成正面 A-pose（动作自由度更大，但每次都要重做风格一致性，
  工作量和风险都上一个台阶）。
- 代价：正面朝向、坐下这类动作以后要重来一次，已在 Non-Goals 里记下。

### 5. 招手用"杖杵地 ＋ 握杖手招手"

- 为什么：立绘里远侧手臂几乎不存在，要造整条远侧臂加袖子是大工程；而"杖离开手、立在地上"
  的逻辑现有代码已有（`PLACED_LEAN`、`PLACED_DX` 与"放下挂灯"那段），可直接复用。
  近侧手本来就举在脸旁，位置正好在视线中心。
- 备选：造远侧整条手臂（贵，且手臂在身体另一侧会被躯干挡）。

### 6. 母图按整数倍降采样，尺寸定为 2048/8 ＝ 256 宽

- 为什么：非整数倍降采样会让边缘发糊，而现有观感依赖整数倍最近邻放大；256 相对现在的 105
  已经有足够信息量表达关节细节，显示倍率仍取整数 2 倍。
- 备选：2048/10 ≈ 205 宽（更接近现在的大小，但与原图不成整数比）；
  2048/4 ＝ 512 宽（屏上 1024，太占地方）。
- 说明：探索过程中口头提过 210×246，它与 2048 不成整数比，这里改按整数比定尺寸。

### 7. 窗口形状继续用包络，不改成每帧剪影

- 为什么：`envelopeShape` 的模式已经存在且不在每帧重算，性能上有保证；肢体摆幅有界，
  包络可以覆盖极限摆位。
- 做法：按骨架极限摆位重算包络（每根链取最大摆角，四肢取动作极限），窗口留边按新包络取。
  必要时按状态分级（待机用小包络、招手用大包络）。
- 备选：每帧重算剪影（`Area` 构造成本高，逐帧做会掉帧）；改成整窗矩形（角色以外会挡鼠标，
  破坏现有体验）。

### 8. 鼠标命中改用骨头包围盒的并集

- 为什么：现有 `bodyAt()` 是固定矩形，骨架把肢体摆出去之后会框不住，也会框住空白；
  按骨头包围盒求并集便宜且足以满足"点得到伸出去的手"这一验收点。
- 备选：每帧生成剪影区域做命中（贵）；保持固定矩形（不满足规格要求）。

### 9. 悬挂实现为"换锚点"，不额外造素材

站立时锚在脚下，拎起时锚在鼠标抓点，重力方向不变，链式部件自然下垂并滞后摆动。

- 需要补的一处：现在只记了鼠标的屏幕坐标，要额外记下按下处在角色内的局部坐标，悬挂支点才正确。
- 为什么优于新做一套悬挂素材：下垂是链式动力学天然给出的结果，零新增素材。

### 10. ComfyUI 只出静态素材，用自带本地图像模板

| 用途 | 选用的自带模板 |
| --- | --- |
| 补关节缝、补被遮挡的躯干 | `flux_fill_inpaint_example.json` |
| 带结构约束的补洞 | `image_qwen_image_instantx_inpainting_controlnet.json` |
| 造抬起的小臂与张开的手掌 | `image_qwen_image_edit_2509.json`、`flux_kontext_dev_basic.json` |

- 精度按最终尺寸倒推：母图只有 256 宽，补洞在 1024 以内完成即可在降采样后看不出差别，
  因此 8 GB 显存够用，**不需要下载视频模型**。
- 不安装自定义节点：本机没有节点管理器，而自带模板已覆盖全部用途。
- 备选：模板库里的云 API 工作流（需要 API key 与额度，走的不是本机显卡）；
  视频模型逐帧（与骨骼路线冲突，且丢掉循环与实时交互）。

### 11. 素材产线以命令驱动

- 为什么：规格要求产出可重复执行、缺失项可逐条核对；ComfyUI 提供 HTTP 接口，
  可以脚本化提交与取回，产出可留痕验收。
- 备选：手工在 ComfyUI 界面点击（不可重复，验收没有凭据）。

### 12. 先做最小验证，再动美术

- 为什么：素材替换是破坏性的（旧精灵图与 `BodyRig` 坐标常量作废），而 Java 侧自写的蒙皮
  是本方案里唯一没有现成代码可抄的部分。先用现有 105×123 图配一个粗糙测试网格把耗时测出来，
  再决定是否全量返工。

## Measured Results

第一版验证（2026-10-15，本机实测）。用现有 105×123 精灵图按 2 倍最近邻放大到 210×246
（与屏上尺寸一致），以髋线为折痕做 ±30 度正弦弯曲，逐帧计时 240 帧、丢弃前 60 帧预热，
渲染进 340×380 缓冲图；求值与绘制分开计时。

| 方案 | 求值（顶点位移） | 绘制（逐三角形贴图） | 合计 |
| --- | --- | --- | --- |
| 网格 12×14（336 个三角形） | 平均 0.008 ms | 平均 0.997 ms，P95 1.286 ms | 约 1.0 ms |
| 网格 24×28（1344 个三角形） | 平均 0.009 ms | 平均 2.233 ms，P95 2.534 ms | 约 2.2 ms |
| 对照：整图直贴（现在的做法） | 无 | 平均 0.077 ms | 0.08 ms |

120 Hz 的每帧预算是 8.33 ms。两种网格密度都留在预算内（约占 12% 与 27%），
求值几乎不花时间，代价全在逐三角形贴图。**结论：继续走蒙皮方案**，
不启用"纯链式骨 ＋ 四肢分段刚体"那条备选。密度上 24×28 仍有余量，
正式蒙皮可按"关节附近加密、其余稀疏"来分配三角形，把预算花在看得见的地方。

验收图在 `_tmp/shots/mesh-check.png`：第一行是弯曲结果，第二行叠加网格线。
0/15/30/45 度四档下关节处都是连续弧线，没有透明缺口、没有硬折角，
相邻三角形之间也没有抗锯齿造成的接缝细线。

## Risks / Trade-offs

- [Java 侧实时蒙皮性能不达标] → 先做最小验证测单帧耗时；若不达标，退到
  "纯链式骨骼 ＋ 四肢分段刚体"（每段独立贴图、靠重叠余量藏缝），仍有明显关节弯折但不需要蒙皮。
- [宽袖补不出来，招手穿帮] → 把"独立袖子层"单列为验收项；补得不好就退回
  "招手幅度小、袖子少动"的版本，并在规格的招手场景里保持可验收。
- [关节重叠余量不足，转出透明缺口] → 拆件时统一在关节两侧留重叠余量，
  验收时逐关节取动作极限角度检查（对应规格里的关节余量场景）。
- [黑底立绘抠底失败] → 现有泛洪判据只认近白背景，必须扩展并补一条"深色背景"验收；
  抠底失败会直接毁掉后续全部素材。
- [素材替换不可逆] → 旧精灵图与拆件逻辑在验证通过前保留，母图与拆件产出放独立目录，可整目录回退。
- [包络变大导致挡鼠标] → 在"不裁掉肢体"与"少挡空白"之间取平衡，必要时按状态分级包络。
- [显存与磁盘] → 补洞分辨率控制在 1024 以内；模型与产出放 D 或 E 盘，不动紧张的 C 盘。
- [风格漂移] → 补全结果必须以最终母图尺寸拼回原图验收，而不是在 2048 分辨率下目测。

## Migration Plan

1. 最小验证：不换素材，用现有 105×123 图配粗糙测试网格，测 Java 侧每帧蒙皮耗时。
2. 素材返工：2048 立绘 → 扩展抠底判据 → 整数倍降采样得到 256 宽透明母图 → 拆件（含关节重叠余量）。
3. ComfyUI 补全缺失区域：关节缝、被发丝与袖子压住的躯干、张开的手掌、抬起的小臂、独立袖子层；
   逐项与原图拼回验收。
4. 骨架接入：骨树、链式动力学（复用 Pendulum）、蒙皮，并把既有踱步等动作改为骨架驱动。
5. 拎起：状态机加拎起状态、记录局部抓点、换悬挂锚点、落地缓冲。
6. 招手：接入补全出来的手臂与袖子素材。
7. 收尾：窗口包络与留边、命中判定、配置项与日志。

回滚策略：素材与骨架定义放在独立目录，旧 `assets/sprites/pet-base.png` 与旧拆件逻辑
在验证通过前不删除，任何一步不达标都可以整目录退回。

## Open Questions

- 母图定 256 宽之后，屏上角色会比现在明显更大；如果实际观感偏大，可在整数倍里退到 205 宽，
  这不影响骨树与拆件结构。
- 包络是否需要按状态分级（待机一种、招手一种）取决于实际摆幅，可在第 7 步实测后决定。
